# 秒杀库存维度不一致修复文档

## 问题是什么

秒杀 Redis 库存按活动维度扣减：

- Redis key：`seckill:stock:{seckillId}`
- 预热时把活动下所有 SKU 的 `total_stock` 求和写入 Redis。

但数据库最终扣减按单个秒杀 SKU 维度执行：

- DB 表：`seckill_sku`
- 扣减条件：`WHERE id = #{seckillSkuId} AND remain_stock >= #{quantity}`

当一个活动包含多个 SKU 时，Redis 可能因为活动总库存充足而放行，但某个具体 SKU 的 DB 库存不足，最终消费失败再回滚。

## 影响

- 多 SKU 秒杀活动会出现大量排队成功但落库失败。
- 用户看到“排队中”后又失败，体验不稳定。
- Redis 回滚和 DB 扣减之间会产生短暂不一致。
- 高并发下失败回滚会放大 Redis、MQ、DB 压力。

## 怎么修复

### 1. Redis 库存改为 SKU 维度

使用已有常量：

```java
SECKILL_SKU_STOCK_KEY = "seckill:sku:stock:%d"
```

预热时对每个 `seckill_sku.id` 写独立库存：

```java
for (SeckillSku sku : skus) {
    String skuStockKey = REDIS_PREFIX + SECKILL_SKU_STOCK_KEY.formatted(sku.getId());
    redisTemplate.opsForValue().setIfAbsent(skuStockKey, String.valueOf(sku.getRemainStock()));
}
```

### 2. Lua 脚本改为扣 SKU 库存

`KEYS[1]` 改为：

```text
mall:seckill:sku:stock:{seckillSkuId}
```

用户去重 key 可以保留活动维度，也可以改成 SKU 维度。若业务规则是“同一活动只能买一次”，保留：

```text
mall:seckill:users:{seckillId}
```

若规则是“同一 SKU 只能买一次”，改为：

```text
mall:seckill:sku:users:{seckillSkuId}
```

### 3. 执行秒杀时先定位 `seckillSku.id`

流程应为：

1. 查询 `seckill` 活动并校验时间。
2. 根据 `seckillId + skuId` 查询 `SeckillSku`。
3. 使用 `seckillSku.getId()` 拼接 Redis 库存 key。
4. Lua 成功后发送 MQ。

示例：

```java
String stockKey = REDIS_PREFIX + SECKILL_SKU_STOCK_KEY.formatted(seckillSku.getId());
String usersKey = REDIS_PREFIX + SECKILL_USERS_KEY.formatted(seckillId);
```

### 4. 回滚时按同一维度恢复

MQ 投递失败或 DB 扣减失败时，必须回滚 SKU 维度库存：

```java
String stockKey = REDIS_PREFIX + SECKILL_SKU_STOCK_KEY.formatted(msg.getSeckillSkuId());
redisTemplate.opsForValue().increment(stockKey, msg.getQuantity());
```

### 5. 详情页展示 SKU 维度库存

详情接口中每个 SKU 都应带自己的 `remainStock`：

```java
String skuStockKey = REDIS_PREFIX + SECKILL_SKU_STOCK_KEY.formatted(sku.getId());
m.put("remainStock", redisTemplate.opsForValue().get(skuStockKey));
```

活动总剩余库存可以作为派生展示字段，由所有 SKU 剩余库存求和得到。

## 验证方式

1. 构造一个活动，SKU A 库存 1，SKU B 库存 100。
2. 并发请求 SKU A 10 次，只允许 1 次进入 MQ。
3. 并发请求 SKU B 不应被 SKU A 的库存影响。
4. Redis 库存、`seckill_sku.remain_stock`、`seckill_order` 成功数量最终一致。
