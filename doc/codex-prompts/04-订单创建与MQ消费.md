# 任务 04：订单创建与 MQ 消费

> 目标：实现秒杀 MQ 消费者 + 订单创建 + 双层幂等（Redis 状态机 + `order.uk_user_activity_item` 唯一键）+ 重投上限。这是整个链路的"落库"环节。

## 前置
- 任务 03 完成（入口已能发 MQ 到 `seckill.order.queue`）
- 权威细节：`doc/秒杀方案分阶段实施计划.md` 3.4.4（秒杀订单创建）、任务 00 消费端流程

## 规格

### 1. mq/SeckillOrderConsumer（`@RabbitListener(queues = "seckill.order.queue")`，手动 ACK）
处理顺序（**不可变**）：
1. 解析消息体（含 messageId/userId/activityId/seckillItemId/spuId/skuId/seckillPrice/price/quantity/addressId）
2. **Redis 状态机幂等**：`SET seckill:order:{userId}:{activityId}:{seckillItemId} 1 NX EX 1800`
   - 设置失败（已存在）→ 读值：
     - `2 SUCCESS` → 直接 `basicAck`（重复消息）
     - `1 PROCESSING` → **不 ACK、延迟重试**（可 `Thread.sleep` 短时间后重入，或直接 NACK requeue，配合重投上限）
     - `3 FAILED` → 删除 Key，重新 SETNX 开始处理（FAILED 允许重试）
3. 调用 `SeckillOrderService.createSeckillOrder(dto)`（见下）
4. 成功 → `SET ... 2 SUCCESS` → `basicAck`
5. `DuplicateKeyException`（`uk_user_activity_item` 冲突）→ 说明订单已存在 → `SET ... 2 SUCCESS` → `basicAck`
6. 其它异常 → `SET ... 3 FAILED` → `basicNack(requeue=false)`；靠队列 `x-delivery-limit=3` 拦截超投，超限消息自动丢弃/死信（记 ERROR 日志 + 后续 Phase 2 接 DLQ）

> 用 `basicAck(deliveryTag,false)` / `basicNack(deliveryTag,false,false)`；不抛异常到框架。

### 2. service/SeckillOrderService.createSeckillOrder(dto)（`@Transactional`）
事务内四件事：
1. **写 `order`**：`order_no`（生成：如 `SECKILL + yyyyMMddHHmmss + 随机`，唯一）、`user_id`、`order_state=1 待付款`、`total_money=pay_money=seckillPrice*quantity`、`post_fee=0`、`order_source=2`、`activity_id`、`seckill_item_id`、`address_id`、`address_snapshot`（按 dto 里的 addressId 查地址快照，可先存 addressId + 简单快照）、`pay_latest_time=now+支付超时(建议 15min)`
2. **写 `order_item`**：`sku_id`/`spu_id`/`name`(可查 SKU 或留空占位)/`cur_price=seckillPrice`（秒杀价快照）/`price`（原价）/`quantity`/`subtotal`/`real_pay`
3. **DB 扣库存（最后防线）**：`UPDATE seckill_item SET seckill_stock=seckill_stock-{quantity} WHERE id={seckillItemId} AND seckill_stock>=quantity`；**影响行数=0 → 抛异常回滚**（触发消费者 FAILED 分支，走重投/补偿，不回补 Redis——因为本单并未落库）
4. **回写 `mq_message.status=4 已完成`**（按 messageId）
- 幂等兜底：`order.uk_user_activity_item(user_id,activity_id,seckill_item_id)` 唯一索引，冲突抛 `DuplicateKeyException`（由消费者捕获视为成功）
- 返回 `{orderId, orderNo}`

### 3. 订单号与地址
- `order_no` 唯一（`uk_order_no`），生成规则保证唯一即可。
- `address_snapshot` 是 JSON：Phase 1 可存 `{addressId}` + 从 user_address 查到的 receiver/contact/address 简要字段；若查不到地址，允许仅存 addressId（按待确认项 3 默认：秒杀时必选地址）。

## 硬性约束
- **订单创建是消费者（seckill-service 内）直接调用应用层方法**，不是 HTTP/Feign。
- 建单事务四步缺一不可；扣库存影响行数=0 必须回滚。
- 禁止对 order/order_item 做 DDL。
- 幂等状态机 Key 必须带 `mall:` 前缀、TTL 1800s。

## 完成标准 / 自测
- `mvn clean compile` 通过。
- 手动向 `seckill.order.queue` 投递一条真实消息（可用任务 03 的 execute 触发）：
  - 消费成功 → `order`/`order_item` 各一行（order_source=2、cur_price=秒杀价）、`mq_message.status=4`、Redis 幂等 Key=2
  - **同一 messageId 重投 3 次 → 订单仍只有 1 行**（Redis SUCCESS 直接 ACK / 唯一键兜底）
- 汇报：消费日志、建单事务日志、幂等重投测试结果。
