# 任务 05：超时取消与库存回补

> 目标：实现秒杀订单支付超时取消（延迟交换机）、库存回补（Redis + DB 双写，幂等）、内部回补接口 `/internal/seckill/orders/{orderNo}/cancel`、补偿任务补全。

## 前置
- 任务 04 完成（建单成功、`mq_message.status=4`）
- 权威细节：`doc/秒杀方案分阶段实施计划.md` 3.4.3、3.4.4（内部回补接口）、3.3（支付超时取消）

## 规格

### 1. 建单后发延迟消息（改 `SeckillOrderService.createSeckillOrder`）
事务提交成功后（`TransactionSynchronization` 或事务外层）：
- `rabbitTemplate.convertAndSend(seckill.delay.exchange, seckill.delay.routing, orderId字符串, msg -> { msg.getMessageProperties().setHeader("x-delay", 支付超时毫秒); return msg; })`
- 支付超时默认 **15 分钟**（900_000ms），与 `pay_latest_time` 一致
- 注意：**只在事务提交成功后发**，避免回滚时误发

### 2. mq/SeckillTimeoutConsumer（`@RabbitListener(queues = "seckill.delay.queue")`，手动 ACK）
- 收到 orderId → 调 `SeckillCompensateService.cancelAndRestore(orderId)`
- 幂等：内部先查订单，`order_state != 1 待付款` → 直接跳过（返回）；成功取消/已取消都 `basicAck`
- 异常 → `basicNack(requeue=false)` + 记 ERROR（靠 `x-delivery-limit` 兜底，Phase 2 接 DLQ）

### 3. service/SeckillCompensateService
**cancelAndRestore(orderId)**（`@Transactional`）：
1. `SELECT order`（含 order_source/activity_id/seckill_item_id/user_id，以及 order_item 的 quantity）
2. 若 `order_source != 2` → 跳过（本服务只管秒杀单）
3. 若 `order_state != 1` → 已处理过，直接返回（幂等）
4. `UPDATE order SET order_state=6 已取消, cancel_reason='支付超时自动取消', cancelled_at=NOW()`（影响行数=0 → 说明已被并发取消，返回）
5. 事务提交后回补库存（或同事务内）：
   - `UPDATE seckill_item SET seckill_stock = seckill_stock + quantity WHERE id = seckill_item_id`
   - `INCRBY mall:seckill:stock:{activityId}:{seckillItemId} quantity`（Redis）
   - 保持 Redis 与 DB 一致
6. 幂等保证：以"order_state 从 1→6 的 CAS"为闸门，重复调用不会重复回补；Phase 2 再落 `seckill_stock_compensate` 流水

**restoreForCancel(orderNo)**：供内部接口调用，逻辑同上，但**不检查 order_state=1**（用户取消时订单可能已付款/其它状态，按业务只对"待付款"回补；其它状态返回且告警）。

### 4. controller/InternalSeckillController（`/internal/**`，**已进 mall.security 白名单**）
```java
@RestController
@RequestMapping(InternalController 内部路径)   // 例如 /internal/seckill
public class InternalSeckillController {
    @PostMapping("/orders/{orderNo}/cancel")
    Result<Void> cancel(@PathVariable String orderNo,
                        @RequestBody StockCompensateDTO dto);
}
```
- 入参：`activityId`/`seckillItemId`/`userId`/`quantity`（订单号为主键，body 作对账参考）
- 调用 `restoreForCancel(orderNo)`；成功 `Result.success()`，失败抛业务异常
- 仅供 order-service Feign 调用（网关已拦外部 `/internal/**`）

### 5. service/SeckillTask 补全
在任务 03 的补偿扫描基础上：
- 定时扫描 `mq_message` status=1 待发送且超时未发 → 重投（已在 03 实现，确认在跑）
- 可选：定时兜底扫 `order` 中 `order_source=2 AND order_state=1 AND pay_latest_time < now` 的订单调 `cancelAndRestore`（延迟交换机故障时的保险；Phase 1 可加，频率 1min）

## 硬性约束
- 延迟交换机/队列名用 seckill 自己的（`seckill.delay.exchange/queue`），**与 order-service 的 `order.delay.*` 独立**。
- 回补 = Redis + DB **双写**；以 order_state CAS 防重复回补。
- 内部接口只做回补，不做订单查询/列表。

## 完成标准 / 自测
- `mvn clean compile` 通过。
- 造一个待付款秒杀订单 → 投递延迟消息（或等超时/触发兜底扫描）：
  - 订单 `order_state` 变 6；`seckill_item.seckill_stock` 与 Redis `mall:seckill:stock:*` 同时 +quantity
  - 重复触发同一 orderId → 库存只回补一次
- 汇报：取消日志、回补前后库存对比（DB + Redis）、幂等验证。
