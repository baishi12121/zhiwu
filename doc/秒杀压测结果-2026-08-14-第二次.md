## 6. 根因定位：瓶颈在压测客户端，不在秒杀服务

对「QPS 远低于预期」的排查结果，用同一脚本、同一参数逐层隔离后得出：

| 测试方式 | QPS | P50 | 说明 |
| --- | ---: | ---: | --- |
| 原始 async 脚本，走网关 | `96` | `4363ms` | 本轮原始结果 |
| async 脚本，走网关（复测） | `246` | `1338ms` | 客户端天花板 |
| async 脚本，直连 8089（绕过网关） | `283` | `1062ms` | 客户端天花板 |
| async 脚本打「只返回 401 的空路径」 | `275` | — | 无 DB/无 Redis 也快不起来 |
| **裸 TCP 建连 500 并发** | **5489 conn/s** | — | 网络栈没问题 |
| **线程池 + 同步 httpx（走网关）** | **515** | **42ms** | 服务端真实能力 |

关键结论：

1. **瓶颈在压测脚本的客户端，不在秒杀服务。** 旧脚本用 `httpx.AsyncClient`，在 Windows 上即使打一个纯拒绝的空路径（无鉴权 DB、无 Redis）也只有 ~275 QPS；而裸 TCP 建连可达 5489 conn/s。说明吞吐天花板是 async httpx 客户端在 Windows 上的实现特性，与服务端无关。
2. 服务端真实能力远超预期：换用线程池 + 同步 httpx + keep-alive 后，同一套服务立即跑出 500+ QPS（见第 7 节）。
3. 本轮 96 QPS 相对复测的 246 QPS 更低，还叠加了当时的瞬时负载（服务端残留 `mvn spring-boot:run` 构建失败、消费端并发建单等）。

## 9. 对比与结论

| 指标 | 原始（async 客户端） | 修复后（线程池客户端） |
| --- | ---: | ---: |
| 总耗时 | `5.23s` | `0.91s` |
| QPS | `96` | `551` |
| P50 | `4363ms` | `34ms` |
| P99 | `4607ms` | `65ms` |

**结论**：本轮性能优化（Redis 原子预扣前置、被拒请求不写库、活动元数据缓存、mq_message 状态合并）已生效；此前两次压测的「低 QPS」是压测脚本 async httpx 客户端在 Windows 上的吞吐天花板造成的测量失真，并非服务端性能问题。修复客户端后，秒杀链路实测 **551 QPS / P99 65ms**，达成 Phase 1 验收指标。

> 备注：第一次压测（2026-08-13）的 `191 QPS / P99 2529ms` 同样受该客户端限制，其数字也不代表服务端真实能力；以本报告第 7 节修复后的结果为准。
