# 商品热度排行榜设计文档

## 一、概述

商品热度排行榜采用 **事件驱动 + 内存聚合 + Redis 有序集合** 的架构，通过 RabbitMQ 解耦点击/下单事件的生产和消费，在消费端对消息进行批量聚合后写入 Redis ZSET，最终通过 `ZREVRANGE` 查询热度排名。

**核心设计目标：**

- 点击/下单事件异步解耦，不阻塞主业务流程
- 消费端批量聚合写入，避免 Redis 写入瓶颈
- 下单权重（+5）高于点击权重（+1），体现购买意向差异

### 消息序列化配置

使用 `Jackson2JsonMessageConverter` 替代默认的 Java 序列化，避免反序列化安全限制。同时通过 `DefaultClassMapper` 做了跨服务的类名映射，使得订单服务（包名 `com.hyf.mallorderservice.entity`）发送的消息能被商品服务（包名 `com.hyf.mallproductservice.entity`）正确解析。

```java
@Bean
public MessageConverter messageConverter() {
    Jackson2JsonMessageConverter converter = new Jackson2JsonMessageConverter();
    DefaultClassMapper classMapper = new DefaultClassMapper();
    // 信任两个服务的 entity 包
    classMapper.setTrustedPackages(
        "com.hyf.mallproductservice.entity",
        "com.hyf.mallorderservice.entity"
    );
    // 将订单服务的类名映射到商品服务的同名类
    Map<String, Class<?>> idClassMapping = new HashMap<>();
    idClassMapping.put("com.hyf.mallorderservice.entity.ProductScoreMessage",
                       ProductScoreMessage.class);
    idClassMapping.put("com.hyf.mallproductservice.entity.ProductScoreMessage",
                       ProductScoreMessage.class);
    classMapper.setIdClassMapping(idClassMapping);
    converter.setClassMapper(classMapper);
    return converter;
}
```

## 五、消息生产端

### 5.1 点击事件发送（商品服务）

```
接口: POST /products/click/{id}
位置: ProductController.clickProduct()
```

**执行步骤：**

1. 接收用户点击的商品 ID
2. 创建 `ProductScoreMessage` 对象，设置 productId、actionType="CLICK"、当前时间戳
3. 调用 `rabbitTemplate.convertAndSend("exchange.product.rank", "routing.product.click", message)`
4. `Jackson2JsonMessageConverter` 将消息序列化为 JSON，并自动添加 `__TypeId__` header
5. 消息路由到 `product.click.queue`，方法立即返回 `200 "success"`

**关键代码：**

```java
@PostMapping("/click/{id}")
public ResponseEntity<String> clickProduct(@PathVariable Long id) {
    ProductScoreMessage message = new ProductScoreMessage();
    message.setProductId(id);
    message.setActionType("CLICK");
    message.setTimestamp(System.currentTimeMillis());
    rabbitTemplate.convertAndSend("exchange.product.rank", "routing.product.click", message);
    return ResponseEntity.ok("success");
}
```

### 5.2 下单事件发送（订单服务）

```
位置: OrderServiceImpl.createOrder()
```

**执行步骤：**

1. 校验订单数据（userId、金额等）
2. 通过 Feign 调用商品服务扣减库存 `productClient.decreaseStock(productId, 1)`
3. 设置订单状态为"未支付"（status=0）
4. 将订单插入数据库 `orderMapper.insert(order)`
5. **发送下单消息**：创建 `ProductScoreMessage`，设置 productId、actionType="ORDER"、时间戳
6. 调用 `rabbitTemplate.convertAndSend("exchange.product.rank", "routing.product.order", message)`

**关键代码：**

```java
orderMapper.insert(order);

ProductScoreMessage message = new ProductScoreMessage();
message.setProductId(order.getProductId());
message.setActionType("ORDER");
message.setTimestamp(System.currentTimeMillis());
rabbitTemplate.convertAndSend("exchange.product.rank", "routing.product.order", message);

return order;
```

> **注意：** 该方法是 `@GlobalTransactional` 标注的 Seata 分布式事务方法，确保"扣库存 + 插订单"的原子性。MQ 消息发送在事务提交前执行，如果后续事务回滚，消息仍会发出——此处采用 **发件即忘** 策略，排行榜数据允许最终一致性。

### 6.2 核心字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `scoreBuffer` | `ConcurrentHashMap<String, Double>` | 内存聚合缓冲区，key=productId 字符串，value=累计热度增量 |

        FLUSH_INTERVAL_MS,     // 100ms

    );
}

## 七、内存聚合与批量刷写（详细流程）

### 7.1 buffer() 方法 — 写入缓冲区

```
输入: ProductScoreMessage (productId=1001, actionType="CLICK"), weight=1.0

┌─────────────────────────────────────────────────┐
│ 步骤1: 空值校验                                  │
│   if (message == null || productId == null)     │
│       → return (丢弃空消息)                     │
│                                                  │
│ 步骤2: 原子累加                                  │
│   scoreBuffer.merge("1001", 1.0, Double::sum)   │
│                                                  │
│   ConcurrentHashMap.merge 原理:                  │
│   - 若 key "1001" 不存在 → put("1001", 1.0)     │
│   - 若 key "1001" 已存在(如 50.0)               │
│     → compute("1001", 50.0 + 1.0) = 51.0       │
│   - 整个过程是原子的，多线程安全                   │
│                                                  │
│ 步骤3: 计数并检查阈值                            │
│   int count = messageCount.incrementAndGet()    │
│   if (count >= 200)                             │
│       → 调用 flush() 立即刷写                    │
└─────────────────────────────────────────────────┘
```

**假设场景：商品 1001 在短时间内被点击 50 次**

```
消息1: merge("1001", 1.0) → buffer = {"1001": 1.0}
消息2: merge("1001", 1.0) → buffer = {"1001": 2.0}
...
消息50: merge("1001", 1.0) → buffer = {"1001": 50.0}

缓冲区只存一条记录，value 是累加后的 50.0
而非 50 条独立记录 → 内存效率极高
```

### 7.2 flush() 方法 — 批量刷写（详细步骤拆解）

```
┌─────────────────────────────────────────────────────────┐
│ 步骤1: synchronized (flushLock) {                        │
│                                                         │
│   步骤1.1: 快速返回检查                                  │
│     if (scoreBuffer.isEmpty())                          │
│         return;  // 无数据，不做事                       │
│                                                         │
│   步骤1.2: 创建快照                                      │
│     Map<String, Double> toFlush = new HashMap<>(buffer) │
│     // 此时 buffer = {"1001": 50.0, "1002": 5.0}        │
│     // 快照 toFlush = {"1001": 50.0, "1002": 5.0}      │
│                                                         │
│   步骤1.3: 清空缓冲区                                    │
│     scoreBuffer.clear()                                 │
│     // buffer 变为 {}，新消息将写入新的空 Map            │
│                                                         │
│   步骤1.4: 重置计数器                                    │
│     messageCount.set(0)                                 │
│     // 计数器归零，重新计数下一批                        │
│                                                         │
│ } // 释放 flushLock，lock 外执行 IO，不阻塞写入线程     │
│                                                         │
│ 步骤2: Redis Pipeline 批量写入                          │
│                                                         │
│   redisTemplate.executePipelined(connection -> {        │
│       // 2.1 将 key 转为 byte[]（一次性操作）            │
│       byte[] key = "product:hot:rank".getBytes()        │
│                                                         │
│       // 2.2 遍历快照，逐条添加到 Pipeline               │
│       for (entry in toFlush):                           │
│           connection.zIncrBy(key, 50.0, "1001")         │
│           // → Redis: ZINCRBY product:hot:rank 50 1001  │
│           connection.zIncrBy(key, 5.0,  "1002")         │
│           // → Redis: ZINCRBY product:hot:rank 5  1002  │
│                                                         │
│       return null;                                      │
│   })                                                    │
│   // Pipeline 将以上 N 条命令打包，一次网络往返发给 Redis │
│                                                         │
│ 步骤3: 异常处理                                         │
│   try { ... log.info("flushed {} entries", N) }         │
│   catch (Exception e) {                                 │
│       log.error("flush failed, {} entries lost", N)     │
│       // 失败则丢弃本次批次，不做重试                    │
│       // 原因: 重试可能导致重复计数，且排行榜允许少量丢失 │
│   }                                                     │
└─────────────────────────────────────────────────────────┘
```

### 7.3 为何用 synchronized 而非其他锁

| 方案 | 问题 |
|---|---|
| **不用锁** | `clear()` 和 `merge()` 并发执行时，刚 merge 的数据可能被 clear 丢失 |
| **ReentrantLock** | 与 synchronized 效果相同，但写法更繁琐，此处无超时/可中断需求 |
| **synchronized** | ✅ 简单够用。锁只保护 swap+clear 这纳秒级操作，Pipeline IO 在锁外执行 |

### 7.4 为何不在 synchronized 内执行 Pipeline

```java
synchronized (flushLock) {
    toFlush = new HashMap<>(scoreBuffer);  // 纳秒级
    scoreBuffer.clear();                    // 纳秒级
    messageCount.set(0);                    // 纳秒级
}
// ← 锁已释放
redisTemplate.executePipelined(...);       // 毫秒级网络 IO
```

> 如果 Pipeline（网络 IO）放在锁内，消息写入线程会被阻塞数十毫秒。swap+clear 是纯内存操作（纳秒级），锁外执行 IO 使得锁几乎不阻塞并发写入。

### 7.5 触发刷写时机

```
     定时触发 (每100ms)               定量触发 (200条消息)
          │                                │
   scheduler.schedule              messageCount >= 200
   AtFixedRate(this::flush)        → flush()
          │                                │
          └────────────┬───────────────────┘
                       ▼
                   flush()
```

- **高流量场景**：消息密集到达，`messageCount` 快速达到 200，定量触发为主，大约每 200 条刷一次
- **低流量场景**：消息稀疏，定时器 100ms 兜底，保证数据不会在内存中停留过久

### 7.6 优雅停机

```java
@PreDestroy
public void shutdown() {
    scheduler.shutdown();   // 停止定时器，不再有新触发
    flush();                 // 最后一次刷写，将残留数据写入 Redis
}
```

> 如果容器直接 kill -9，这部分数据会丢失。排行榜数据允许最终一致，可接受。

## 八、查询端

### 接口

```
GET /products/hot-rank?topN=10
```

### 位置

`ProductServiceImpl.getHotProductRank()`

### 执行步骤

```
步骤1: 参数校验
  if (topN <= 0) → return []

步骤2: Redis ZREVRANGE 命令
  ZREVRANGE product:hot:rank 0 9 WITHSCORES
  // 时间复杂度: O(log N + M)，N=集合大小，M=topN

步骤3: 结果转换为 List<Long>
  Set<TypedTuple<String>> → List<Long> productIds
  按 score 从高到低排列

步骤4: 异常降级
  若 Redis 不可用 → catch Exception → return []
  // 排行榜非核心功能，不可用时返回空列表，不影响商品主流程
```

## 九、关键技术点总结

| 技术点 | 方案 | 说明 |
|---|---|---|
| 事件解耦 | RabbitMQ Topic Exchange | 点击/下单事件异步处理，不阻塞主流程 |
| 跨服务序列化 | Jackson2JsonMessageConverter | JSON 序列化，替代不安全的 Java 序列化 |
| 跨服务类名映射 | DefaultClassMapper.setIdClassMapping() | 解决不同服务的包名不同问题 |
| 内存聚合 | ConcurrentHashMap.merge() | 原子累加同 productId 的热度值 |
| 线程安全计数 | AtomicInteger | 无锁计数，达到阈值触发刷写 |
| 定时刷写 | ScheduledExecutorService | 100ms 兜底，保证低流量时数据及时落盘 |
| 批量写入 | Redis Pipeline (executePipelined) | N 个 ZINCRBY 合并为一次网络往返 |
| 锁策略 | synchronized + swap | 持锁做纳秒级内存交换，放锁做毫秒级 IO |
| 异常降级 | try-catch 返回空列表 | Redis 不可用时不影响商品主流程 |
| 优雅停机 | @PreDestroy flush() | 容器关闭前最后一次刷写，尽量减少数据丢失 |
