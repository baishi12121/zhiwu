## 一、总体原则

### 1.1 分阶段理由

原生产级方案要求 Redis Cluster 3主3从、RabbitMQ Cluster + Quorum Queue、库存分片、全链路对账等重型基础设施。但项目当前处于 skeleton/DDD 重构阶段，业务服务多未实现，直接全量落地存在以下问题：

- 基础设施落差大，本地无法验证 Cluster 模式有效性
- 业务服务未跑通时引入复杂 MQ 方案，优先级倒置
- 一次性引入 12+ 节点 LangGraph 级复杂度，调试与排障成本极高
- 部分设计（如批量刷库部分失败处理）在高并发未达前无法验证

### 1.2 分阶段核心思想

```text
Phase 1：先跑通核心链路（单机版最小闭环）
   ↓ 验收通过
Phase 2：补齐可靠性（重试、死信、补偿、对账）
   ↓ 验收通过
Phase 3：升级高可用（Cluster、分片、降级熔断）
```

每个 Phase 必须满足：
- **可独立交付**：完成后系统可用，不依赖下一阶段
- **可验证**：有明确的验收标准与压测指标
- **可回滚**：失败时不影响已有功能

## 二、跨阶段技术决策（必须先对齐）

以下决策在三个 Phase 中均保持一致，需在动工前确认。

### 2.1 业务字段语义统一

**问题**：原方案 messageId 用 `productId`（SPU 维度），但 order 表唯一索引用 `seckill_item_id`（SKU 维度），维度不一致会导致幂等失效。

**决策**（已确认）：全链路统一为 **SKU 维度**，以 `seckill_item_id` 为核心业务标识。

```text
messageId = userId:activityId:seckillItemId
```

| 用途 | Key/字段 | 维度 |
|---|---|---|
| MQ 业务消息ID | `messageId` | `userId:activityId:seckillItemId` |
| 本地消息表唯一键 | `mq_message.message_id` | 同上 |
| Redis 幂等 Key | `seckill:order:{userId}:{activityId}:{seckillItemId}` | 同上 |
| 订单表唯一索引 | `order.uk_user_activity_item(user_id, activity_id, seckill_item_id)` | 同上 |
| Redis 库存 Key | `seckill:stock:{activityId}:{seckillItemId}` | SKU 维度 |
| Redis 限购 Key | `seckill:user:{activityId}:{seckillItemId}:{userId}` | SKU 维度 |

> ✅ 已确认切换。**已修订**（2026-08-12）：同步修订 [基于Redis和MQ实现秒杀订单加购.md](./基于Redis和MQ实现秒杀订单加购.md) 的 `productId` 表述，并补齐与 SKU 维度配套的修改：
> - 第四节《业务 messageId 设计》、第五节《为什么使用业务 messageId》、第六节《messageId 示例》、第十二节《秒杀成功生成 messageId》、第四十四节《核心 Redis Key》、第四十七节《最终方案总结》（统一业务 ID 部分）
> - 1.1 / 四十三节 `mq_message` DDL：`product_id` → `seckill_item_id`（SKU 维度）+ 冗余 `spu_id`/`sku_id`/`quantity`
>
> ⚠️ **Redis Key 前缀**：上表 Key 省略 `mall:` 前缀以便阅读，实现时按 `MallConstants.REDIS_PREFIX` 统一加 `mall:` 前缀。

### 2.2 订单状态枚举统一

**问题**：原方案秒杀订单状态用 `0-待支付 1-已支付 2-已取消 3-已完成`，与 init.sql 的 `order.order_state`（`1待付款 2待发货 3待收货 4待评价 5已完成 6已取消`）冲突。

**决策**：秒杀订单与普通订单共用 `order.order_state` 枚举，不引入独立状态机。

| order_state | 含义 | 秒杀场景语义 |
|---|---|---|
| 1 | 待付款 | 秒杀成功待支付 |
| 2 | 待发货 | 已支付待发货 |
| 3 | 待收货 | 已发货 |
| 4 | 待评价 | 已收货 |
| 5 | 已完成 | 交易完成 |
| 6 | 已取消 | 超时取消/用户取消/系统回滚 |

### 2.4 延迟队列实现

**决策**：延续 [隐患修复-07](./隐患修复-07-RabbitMQ延迟交换机配置.md) 的方案，使用 `rabbitmq_delayed_message_exchange` 插件。

**理由**：
- 项目已采用此方案，保持一致
- 避免 TTL+DLX 的"队头阻塞"问题（不同延迟时间的消息会互相阻塞）
- 定时任务扫描 `pay_latest_time` 作为兜底

## 三、Phase 1：MVP 最小闭环

### 3.1 目标

在单机基础设施上跑通"秒杀入口 → MQ → 订单创建"的核心链路，**以正确性验证为主**，性能与高可用留给 Phase 2/3。

**核心指标**：
- 单机压测 500 QPS，无超卖、无丢消息、无重复订单
- 端到端 P99 < 800ms（不含支付）
- 全链路功能正确性 100% 通过（异常场景不丢数据）

### 3.2 基础设施要求

| 组件 | 要求 | 当前状态 |
|---|---|---|
| Redis | 单机即可，无需 Cluster | ✅ 本地已安装（`127.0.0.1:6379`，非 docker-compose 提供） |
| RabbitMQ | 单机 + Durable Queue + Persistent 消息 | ✅ 本地已安装（`localhost:5672`，非 docker-compose 提供），需确认延迟插件已装 |
| MySQL | 单机 | ✅ 本地已安装，表结构已扩展 |
| Nacos | 单机 | ✅ 本地已安装 提供（`127.0.0.1:8848`） |
| Sentinel | 单机 | ✅ 本地已安装 提供（`localhost:8858`），仅 marketing-service 引用 |

> ⚠️ 注意：`docker-compose.yml` 仅提供 Nacos + Sentinel，**Redis 和 RabbitMQ 是本地安装的服务**，部署文档需明确说明，避免新成员误以为基础设施全部由 docker-compose 提供。

**不需要**：Redis Cluster、RabbitMQ Cluster、Quorum Queue、库存分片。

### 3.3 功能范围

> **范围说明**（已确认）：Phase 1 **仅后端 + 压测验证**，不改造 uniapp 前端秒杀页面。前端联调放 Phase 2。

#### 做什么

| 模块 | 实现内容 |
|---|---|
| Redis 库存预热 | 按 `seckill_item.id` 维度预热到 `seckill:stock:{activityId}:{seckillItemId}`，仅预热「已启用且在活动窗口内」的活动；**触发时机**：定时任务在活动开始前扫描预热，或管理端手动触发；同时缓存商品项元数据 `seckill:item:{seckillItemId}`（spu_id/sku_id/秒杀价/原价/limit_per_user）供入口读取，避免每请求查库 |
| 活动窗口校验 | 秒杀入口校验 `seckill_activity.start_time/end_time`，未开始/已结束直接拒绝 |
| Lua 原子扣库存 | 单 Key 扣减（`DECRBY quantity`）+ 用户限购（`INCRBY` 累计，支持 `limit_per_user>1`） |
| 本地消息表 | 写入 `mq_message`，状态机流转（待扣库存→待发送→已发送→已完成） |
| MQ 发送 | Spring AMQP + Publisher Confirm，ACK 后更新消息表 |
| MQ 消费 | 手动 ACK，事务提交后确认，单条处理（不做批量刷库） |
| 消费重试上限 | 防止毒消息热循环：重投次数超限后置 `mq_message` 失败并停止重投（`x-delivery-limit` 或本地计数） |
| 订单创建 | 消费者（seckill-service 内）调用本服务应用层建单：创建 `order` + `order_item`，**事务内扣减 `seckill_item.seckill_stock`**（`UPDATE ... WHERE 库存>=quantity`，影响行数=0 则回滚并触发补偿，DB 超卖最后防线），成功后**回写 `mq_message.status=4`**；消息携带完整快照不查库 |
| 幂等保障 | Redis 状态机（PROCESSING/SUCCESS/FAILED）+ MySQL UNIQUE KEY |
| 秒杀结果查询 | `GET /seckill/{activityId}/result?seckillItemId=xxx`，以 `mq_message.status` 为状态来源 |
| 支付超时取消 | 延迟交换机 + 定时任务兜底 |

#### 不做什么（明确推迟到 Phase 2/3）

| 推迟项 | 原因 | 归属阶段 |
|---|---|---|
| 批量刷库 | 单条处理足以应对 Phase 1 的 QPS | Phase 2 |
| DLQ 死信队列 | 简单重试即可，DLQ 需要额外消费链路 | Phase 2 |
| 指数退避重试 | 固定次数重试即可 | Phase 2 |
| 库存补偿闭环 | Phase 1 用超时取消 + 手动回补 | Phase 2 |
| 全链路对账 | 数据量小，人工对账即可 | Phase 2 |
| Redis Cluster | 单机够用 | Phase 3 |
| Quorum Queue | 单机无需多副本 | Phase 3 |
| 库存分片 | 无热点商品场景 | Phase 3 |
| 降级熔断 | 流量未达阈值 | Phase 3 |

### 3.4 关键设计

#### 3.4.1 Redis Key 规范

```text
# 秒杀库存（SKU 维度，值=seckill_item.seckill_stock 预热值）
seckill:stock:{activityId}:{seckillItemId}

# 商品项元数据缓存（预热时写入：spu_id/sku_id/秒杀价/原价/limit_per_user，供入口读取拼消息，TTL=活动剩余时长）
seckill:item:{seckillItemId}

# 用户限购记录（SKU 维度，值=累计已购数量）
seckill:user:{activityId}:{seckillItemId}:{userId}

# 消费幂等状态机
seckill:order:{userId}:{activityId}:{seckillItemId}
# 值：1=PROCESSING 2=SUCCESS 3=FAILED
# TTL：30分钟
```
> ⚠️ 上述 Key 省略前缀，实现时统一加 `mall:` 前缀（`MallConstants.REDIS_PREFIX`），模板常量统一定义在 `MallConstants`，勿散落硬编码。

#### 3.4.2 Lua 脚本（简化版，不涉及 Hash Tag）

```text
KEYS[1] = seckill:stock:{activityId}:{seckillItemId}
KEYS[2] = seckill:user:{activityId}:{seckillItemId}:{userId}
ARGV[1] = 用户限购Key的TTL（秒，建议=活动剩余时长，兜底 30 分钟）
ARGV[2] = quantity（本次购买数量，≥1）
ARGV[3] = limit_per_user（seckill_item.limit_per_user）

逻辑：
  1. quantity < 1 → 返回 -2
  2. GET KEYS[2]（累计已购数），若 已购 + quantity > limit_per_user → 返回 -1
  3. GET KEYS[1]，若库存 < quantity → 返回 0
  4. DECRBY KEYS[1] quantity
  5. INCRBY KEYS[2] quantity + EXPIRE ARGV[1]
  6. 返回 1

返回值：1成功 0库存不足 -1已达限购 -2非法数量
```
> `limit_per_user` 默认 1。若业务不开放多件限购，入口把 `quantity` 恒置 1 即可。

#### 3.4.3 MQ 配置

| 配置项 | 值 | 说明 |
|---|---|---|
| Exchange | `seckill.exchange`（Direct，Durable） | 秒杀订单交换机 |
| Queue | `seckill.order.queue`（Durable） | 秒杀订单队列 |
| RoutingKey | `seckill.order` | |
| 消息持久化 | `DeliveryMode.PERSISTENT` | |
| Publisher Confirm | 开启 | 异步 ConfirmCallback |
| Consumer ACK | 手动 | `acknowledge-mode: manual` |
| 消费重投上限 | `x-delivery-limit: 3` 或消费端本地计数 | 防毒消息热循环，超限停投并置 `mq_message` 失败 |
| 延迟交换机 | `seckill.delay.exchange`（x-delayed-message） | 秒杀订单支付超时取消：seckill-service **声明自己的延迟交换机/队列**（`seckill.delay.exchange` / `seckill.delay.queue`），建单时发带 `x-delay` 头的消息，消费时取消订单并回补库存（Redis + DB）；与 order-service 的 `order.delay.exchange` 相互独立，互不干扰 |

#### 3.4.4 接口契约

**秒杀入口**（seckill-service）：
```text
POST /seckill/{activityId}/execute
Header: Authorization: Bearer <token>
Body: { "seckillItemId": 123, "quantity": 1, "addressId": 5001 }

执行顺序：token（接口侧自校验防直连伪造）→ 读 `seckill:item:{seckillItemId}` 元数据 → 活动时间窗口校验 → **写 `mq_message`（待扣库存）** → Lua 扣库存 → 成功置「待发送」并发 MQ，失败置「发送失败」并返回错误
Response:
  - 秒杀成功：{ "code":200, "data": { "status":"queued", "messageId":"8888:1001:2001" } }
  - 库存不足：{ "code":4001, "message":"库存不足" }
  - 重复秒杀：{ "code":4002, "message":"您已购买过该商品" }
  - 活动未开始/已结束：{ "code":4003, "message":"活动未开始或已结束" }
```

**秒杀结果查询**（seckill-service，**状态来源为 `mq_message.status`**）：
```text
GET /seckill/{activityId}/result?seckillItemId=123
Header: Authorization: Bearer <token>

状态映射：
  mq_message.status ∈ {0待扣库存, 1待发送, 2已发送} → pending
  mq_message.status = 4已完成                      → ordered（orderId/orderNo 从 order 表按 uk_user_activity_item 查回）
  mq_message.status = 3发送失败                    → failed
Response:
  { "code":200, "data": { "status":"pending|ordered|failed", "orderId":"...", "orderNo":"..." } }
```
> ⚠️ 结果查询**不能**以 Redis 状态机 key 为来源：该 key 是消费端消费时才 SETNX 创建的，execute 刚返回 queued 时它还不存在，无法区分 pending 与 failed。

**秒杀订单创建**（seckill-service 应用层方法，由同服务内的 MQ 消费者直接调用，**非 HTTP/Feign**）：
```text
方法：OrderApplicationService.createSeckillOrder(CreateSeckillOrderDTO)
入参 DTO = {
  "messageId": "8888:1001:2001",
  "userId": 8888,
  "activityId": 1001,
  "seckillItemId": 2001,
  "skuId": 3001,
  "spuId": 4001,
  "seckillPrice": 99.00,
  "price": 129.00,
  "quantity": 1,
  "addressId": 5001
}
事务内处理：
  ① 写 `order`（order_source=2, activity_id, seckill_item_id）+ `order_item`（cur_price=seckillPrice, price=原价）
  ② 扣减 `seckill_item.seckill_stock`（UPDATE ... WHERE 库存>=quantity；影响行数=0 → 回滚，触发补偿）
  ③ 回写 `mq_message.status=4`（已完成）
返回：{ orderId, orderNo }
```

**内部库存回补接口**（seckill-service，供 order-service 取消秒杀订单时 Feign 调用）：
```text
POST /internal/seckill/orders/{orderNo}/cancel
Body: { "activityId":1001, "seckillItemId":2001, "userId":8888, "quantity":1 }

处理：回补 Redis 库存（seckill:stock 增 quantity）+ 回补 `seckill_item.seckill_stock`（DB），两者保持一致
幂等：以 messageId/订单号防重复回补（Phase 2 用 seckill_stock_compensate 流水）
Response: { "code":200 }
```

- 消息丢失率 = 0（含各种异常注入场景）

- Phase 1 全部验收项通过

### 4.3 功能范围

#### 新增

| 模块 | 实现内容 |
|---|---|

### 4.4 关键设计

#### 4.4.1 DLQ 与重试链路

```text
seckill.order.queue
    ↓ 消费失败
seckill.order.retry.queue (TTL=1s, DLX=seckill.dlx)
    ↓ 再次失败（重试1）
seckill.order.retry.queue (TTL=5s, DLX=seckill.dlx)
    ↓ 再次失败（重试2）
seckill.order.retry.queue (TTL=30s, DLX=seckill.dlx)
    ↓ 仍失败
seckill.order.dlq (死信队列，人工处理)
```

> 简化实现可用 Spring Retry + 本地重试，DLQ 仅作为最终兜底。

#### 4.4.2 批量刷库流程

```text
MQ消息 → 消费者 → BatchQueue（内存缓冲）
                       ↓
            双阈值触发：size>=1000 OR 距上次刷库>=1s
                       ↓
            批量 INSERT INTO `order` ... ON DUPLICATE KEY UPDATE
                       ↓
            MySQL 事务提交成功
                       ↓
            批量更新 Redis 幂等状态为 SUCCESS + 批量 ACK
```

**部分失败处理**：
- 唯一键冲突 → 视为成功，正常 ACK
- 其他异常 → 单条 NACK，不回滚整批

#### 4.4.3 库存补偿流水表（新增）

```sql
CREATE TABLE `seckill_stock_compensate` (
  `id`              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `message_id`      VARCHAR(128)    NOT NULL  COMMENT '关联业务messageId',
  `activity_id`     BIGINT UNSIGNED NOT NULL,
  `seckill_item_id` BIGINT UNSIGNED NOT NULL,
  `user_id`         BIGINT UNSIGNED NOT NULL,
  `quantity`        INT             NOT NULL,
  `compensate_type` TINYINT         NOT NULL  COMMENT '1下单失败 2支付超时 3用户取消 4对账偏差',
  `status`          TINYINT         NOT NULL DEFAULT 0 COMMENT '0待处理 1已完成 2失败',
  `create_time`     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_message_id_type` (`message_id`, `compensate_type`),
  KEY `idx_status` (`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='秒杀库存补偿流水';
```

#### 4.4.4 对账维度

| 对账项 | 数据源 | 频率 | 偏差处理 |
|---|---|---|---|
| 本地消息表 vs MQ | `mq_message` 待发送数 vs 队列积压数 | 分钟级 | 补发消息 |
| MQ 消费 vs 订单表 | 已消费 messageId vs `order` 中 `order_source=2` 记录 | 分钟级 | 告警 + 补单 |
| Redis 库存 vs MySQL | `seckill:stock:*` vs `seckill_item.seckill_stock` | 小时级 | 以 MySQL 为准校准 Redis |
| 订单数 vs 初始库存 | `order` 中秒杀订单数 vs `seckill_item.seckill_stock` 扣减量 | 活动结束 | 超卖告警人工介入 |

### 4.5 验收标准

| 验收项 | 标准 | 验证方式 |
|---|---|---|
| 异常注入不丢消息 | DB宕机/网络断开/消费者kill后恢复，消息最终全部落库 | 混沌测试 |

| 对账发现偏差 | 手动制造偏差，对账任务能发现并告警 | 人工改数据 |
| 定时补偿幂等 | 同一条待发送记录被多次扫描，只投递一次 | 调整扫描频率测试 |

### 5.4 关键设计

#### 5.4.1 库存分片

```text
原 Key：seckill:stock:{activityId}:{seckillItemId}

分片 Key（N=8）：
  seckill:stock:{activityId_0}:{seckillItemId}
  seckill:stock:{activityId_1}:{seckillItemId}
  ...
  seckill:stock:{activityId_7}:{seckillItemId}
```

- 预热时总库存均匀分配到 8 个分片
- 秒杀请求轮询分片，扣减失败换下一分片
- 不同分片 Key 的 Hash Tag 不同，分散到不同 Redis 节点

#### 5.4.2 降级策略

| 故障场景 | 降级动作 | 用户感知 |
|---|---|---|
| Redis 部分节点宕机 | Cluster 自动切换从节点 | 无感 |
| Redis 全部宕机 | 降级为同步DB扣库存 + 强限流 | 部分用户看到"系统繁忙" |
| RabbitMQ 宕机 | 消息发送重试超阈值后回滚Redis库存，返回秒杀失败 | 用户看到"秒杀失败" |
| MySQL 高负载 | 自动调小批量大小、拉长刷库间隔、上游限流 | 响应变慢 |
| 消费者全部宕机 | 上游限流，避免 MQ 积压爆仓 | 响应变慢 |

### 5.5 验收标准

| 验收项 | 标准 | 验证方式 |
|---|---|---|
| Redis 主从切换 | kill 一个主节点，秒杀不中断 | 集群故障注入 |
| RabbitMQ 节点故障 | kill 一个 Broker，消息不丢 | 集群故障注入 |
| 热点商品压测 | 单商品 1万 QPS，无超卖 | 压测 |
| 降级生效 | 模拟 Redis 宕机，自动降级DB扣库存 | 故障注入 |
| 熔断生效 | 模拟慢调用，Sentinel 触发熔断 | 故障注入 |

1. **限购规则**：用户限购是"同一活动只能买一次"还是"同一 SKU 只能买一次"？

   - 选项B：SKU 维度，Redis Key 用 `seckill:user:{activityId}:{seckillItemId}:{userId}`（**当前方案默认采用**，与 `order.uk_user_activity_item` 唯一索引一致）

   - **影响**：决定库存回补接口是否需要写 Redis，以及活动总库存与可售库存的语义分离；同时影响对账公式（Redis 库存 = 初始 − 未取消订单数）

   - 选项B：秒杀下单暂不填地址，支付成功后补填
   - **影响**：决定 execute 接口是否必传 `addressId`，以及内部下单接口契约
