# 管理后台订单管理设计方案

> 本文档基于 zhiwu-mall 当前代码与 schema 现状（2026-08-13 核实），为 `frontend-admin` + `mall-admin-service` 补齐**订单管理（含发货）**模块的设计方案。
>
> **本文档定位**：方案对齐与边界划分，开发可直接照做。不包含逐行代码实现。

> **修订记录（2026-08-13）**：初版。依据对 `mall-admin-service` / `mall-order-service` / `sql/init.sql` / `frontend-admin` 的代码走查形成。

---

## 一、现状盘点

### 1.1 缺口

| 端 | 现状 |
|---|---|
| 后端 admin（`mall-admin-service` 8088） | 已有 auth/banner/product/sales/**seckill**/user 六组 controller，**无订单模块** |
| 前端 admin（`frontend-admin`） | 路由/菜单为 dashboard/products/banners/seckill/users，**无 orders 视图**；`StatusTag.vue` 仅支持两态（启用/停用），订单 6 态需新组件 |
| 订单状态机 | order-service 仅实现 1→2（支付）、3→4（确认收货），**2→3（发货）这一环缺失**，`order_status_log.operator` 支持 `ADMIN` 但从未使用 |

### 1.2 可复用的既有资产（均已核实存在）

| 资产 | 位置 | 说明 |
|---|---|---|
| `order` 表 | `sql/init.sql:397` | 含 `order_state`(1待付款…6已取消)、收货人三字段、`shipped_at`、`order_source`(1普通/2秒杀)、`activity_id`/`seckill_item_id`；无物流公司/运单号字段 |
| `order_item` 表 | `sql/init.sql:438` | 商品快照（name/image/attrs_text/quantity/real_pay） |
| `order_status_log` 表 | `sql/init.sql:460` | 状态流转日志，`operator` 取 USER / SYSTEM / ADMIN |
| **`logistics_company` 表** | `sql/init.sql:475` | 快递公司，**已种 3 条**：顺丰 SF / 中通 ZTO / 圆通 YTO |
| **`order_logistics` 表** | `sql/init.sql:487` | `order_id` 唯一(`uk_order`) + `company_id` + `logistics_no` |
| **`order_logistics_track` 表** | `sql/init.sql:499` | 物流轨迹（content / occur_time / sort_order） |
| admin 直连库模式 | `SalesMapper` / `AdminUserServiceImpl` / `AdminSeckillServiceImpl` | MyBatis-Plus `LambdaQueryWrapper` + `PageResult.of` + `@Transactional` + `BizException` |
| 网关鉴权 | `AuthGlobalFilter` | `/admin/**` 除 `/admin/login`、`/admin/health` 外均须 token，admin-service 自验签 |

> ⚠️ **物流三表目前全库零代码引用**——只有 DDL 与种子数据，没有任何 Entity/Mapper/Service 使用。本方案将首次消费它们。

## 二、架构决策

### 2.1 归属：订单管理落在 `mall-admin-service`，直连共享 `mall` 库，不走 Feign

- `SalesMapper` 已经在直接聚合 `order`/`order_item`，admin 直读订单是既定事实；
- 发货只改状态 + 写物流表，**不涉及库存/优惠券**（那些只在「取消/退款」时才有跨服务/库存回补问题），单库本地事务即可，无分布式一致性负担；
- 状态机校验（仅 `2` 可发货）用**条件更新**实现，天然防并发双击幂等。

> 对比选项：在 order-service 加管理端内部接口再 Feign 调用。优点是把订单状态机收敛到 order-service，但与 admin 现有 sales/seckill/user 全部直连库的模式不一致，且发货不涉及跨服务资源，收益有限。**不采用。**

### 2.2 边界：Phase 1 vs Phase 2

| Phase 1（本期交付） | Phase 2（扩展点，本期不做） |
|---|---|
| 订单列表（分页 + 多条件筛选） | 管理员取消 / 退款（动库存/秒杀回补/退券，跨服务） |
| 订单详情（含状态时间线 + 物流信息） | 物流轨迹对接第三方（快递100/快递鸟）回填 track，C 端展示 |
| **发货**（状态 2→3 + 物流落库） | 物流公司 CRUD、订单导出 CSV、待发货数看板 |
| 物流公司下拉（供发货弹窗选择） | 订单备注/改价等运营操作 |

## 三、数据层

**无需新建表**。物流三表已定义于 `sql/init.sql:473-507`，`logistics_company` 已种 3 条（SF/ZTO/YTO）。

唯一前置动作：**确认运行中的 mall 库已应用这 3 张表**。若库建于秒杀迁移之前（早于这三段 DDL），补跑一次建表 + 种子 SQL。发货复用 `order.shipped_at`，不新增列。

发货涉及的表写入（单本地事务内完成）：

| 表 | 写入 | 唯一性保障 |
|---|---|---|
| `order` | `order_state=3`、`shipped_at=NOW()` | 条件 `WHERE id=? AND order_state=2` |
| `order_logistics` | `company_id`、`logistics_no` | `uk_order` 存在则 update（重复发货覆盖） |
| `order_logistics_track` | 首条轨迹：`已由{公司名}揽收，运单号{logisticsNo}` | 每次发货插入 |
| `order_status_log` | `from_state=2 → to_state=3`、`operator=ADMIN`、remark=管理员发货 | 幂等由发货条件更新保证 |

## 四、后端接口契约（全部 `/admin/orders`）

> 响应统一 `Result<T>` / `PageResult<T>`（`{ code, message, data }`），错误走 `BizException` + `GlobalExceptionHandler`。经网关 `/admin/**`，已带 token。

### 4.1 `GET /admin/orders` — 订单分页列表

请求参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `orderState` | Integer | 订单状态 1-6，不传=全部 |
| `orderSource` | Integer | 来源 1普通 / 2秒杀，不传=全部 |
| `keyword` | String | 订单号 / 收货人 / 收货手机 模糊匹配 |
| `start` / `end` | LocalDate | 下单时间范围（含） |
| `page` / `pageSize` | int | 分页（`PageQuery`） |

响应行字段：

```
id, orderNo, userId, nickname, orderState, orderSource,
receiverContact, receiverMobile, payMoney,
itemImage, itemName, itemCount, totalNum,
createTime, shippedAt
```

SQL 要点（Mapper `@Select`，与 `SalesMapper`/`selectPageWithItemCount` 同风格；`order`/`user` 为 MySQL 关键字，均加反引号）：

```sql
SELECT o.id, o.order_no, o.user_id, u.nickname, o.order_state, o.order_source,
       o.receiver_contact, o.receiver_mobile, o.pay_money, o.create_time, o.shipped_at,
       (SELECT oi.image FROM order_item oi WHERE oi.order_id = o.id ORDER BY oi.id LIMIT 1) AS item_image,
       (SELECT oi.name  FROM order_item oi WHERE oi.order_id = o.id ORDER BY oi.id LIMIT 1) AS item_name,
       (SELECT COUNT(*)          FROM order_item oi WHERE oi.order_id = o.id) AS item_count,
       (SELECT COALESCE(SUM(oi.quantity),0) FROM order_item oi WHERE oi.order_id = o.id) AS total_num
FROM `order` o LEFT JOIN `user` u ON u.id = o.user_id
WHERE 1=1
  [AND o.order_state = #{orderState}]
  [AND o.order_source = #{orderSource}]
  [AND (o.order_no LIKE #{kw} OR o.receiver_contact LIKE #{kw} OR o.receiver_mobile LIKE #{kw})]
  [AND o.create_time >= #{start} AND o.create_time < DATE_ADD(#{end}, INTERVAL 1 DAY)]
ORDER BY o.create_time DESC
```

### 4.2 `GET /admin/orders/{id}` — 订单详情

返回结构：

```
order 主单（orderNo/payType/payChannel/buyerMessage/cancelReason/receiver* / payMoney/postFee/discountAmount/createTime/paidAt/shippedAt...）
items[]           订单明细，联表补 skuCode
statusLogs[]      order_status_log 按时间升序（前端渲染时间线，标注 operator 用户/系统/管理员）
logistics         已发货时返回：{ companyName, companyCode, logisticsNo, track[] }，未发货为 null
```

订单不存在 → `BizException(NOT_FOUND)`。

### 4.3 `PUT /admin/orders/{id}/ship` — 发货

请求体：

```json
{ "companyId": 1, "logisticsNo": "SF1234567890" }
```

校验：`companyId` `@NotNull` 且物流公司存在；`logisticsNo` `@NotBlank`。

核心逻辑（`@Transactional`）：

```java
public Map<String,Object> ship(Long orderId, OrderShipRequest req) {
    // 1. 校验物流公司存在（LogisticsCompanyMapper.selectById）
    // 2. 条件更新防并发：仅 待发货(2) 可发货
    int affected = orderMapper.shipOrder(orderId);
    //    UPDATE `order` SET order_state=3, shipped_at=NOW()
    //    WHERE id=#{orderId} AND order_state=2
    if (affected == 0) {
        throw new BizException(ResultCode.ORDER_STATUS_ILLEGAL, "订单非待发货状态，无法发货");
    }
    // 3. upsert order_logistics（uk_order 存在则 update，重复发货覆盖运单信息）
    // 4. 写 order_logistics_track 首条轨迹：「您的包裹已由{公司名}揽收，运单号{logisticsNo}」
    // 5. 写 order_status_log(from=2, to=3, operator=ADMIN, remark="管理员发货")
    return getDetail(orderId);   // 返回更新后详情
}
```

幂等性：`WHERE order_state=2` 保证并发双击只有一次成功；已发货/其他状态订单再次发货返回明确错误，不重复写物流。秒杀订单（`order_source=2`）发货与秒杀库存无关，天然兼容，无需特殊处理。

### 4.4 `GET /admin/orders/logistics/companies` — 物流公司下拉

`SELECT id, name, code, tel FROM logistics_company ORDER BY sort_order`。当前返回 3 条（SF/ZTO/YTO）。

### 6.2 OrderStatusTag（6 态配色，对齐 `dict` 的 order_status 1-6）

| order_state | 文案 | 类型 |
|---|---|---|
| 1 | 待付款 | default |
| 2 | 待发货 | warning |
| 3 | 待收货 | info |
| 4 | 待评价 | success |
| 5 | 已完成 | success |
| 6 | 已取消 | error |

秒杀订单在来源列额外打一个 `error`-type 小 tag「秒杀」。

### 6.3 OrdersView 页面结构（对齐 UsersView/SeckillView 布局）

- **状态 Tab**（`n-tabs`）：全部 / 待付款 / 待发货 / 待收货 / 待评价 / 已完成 / 已取消，映射 `order_state`；「待发货」显示待处理数量徽标，引导运营优先发货。
- **工具栏**：订单号/收货人/手机号 输入、来源筛选（普通/秒杀）、下单时间 `n-date-picker` range。
- **表格列**：订单号（等宽字体）｜商品（首图缩略 + 名称 + `N 件`）｜收货人（姓名/手机）｜实付金额｜来源｜状态（`OrderStatusTag`）｜下单时间｜操作（**详情** / **发货**）。
- **发货弹窗**（`n-modal`，仅待发货行可点）：物流公司 `n-select`（数据来自 `/admin/orders/logistics/companies`）+ 运单号 `n-input`，前端空值校验与后端一致；提交走 `PUT /admin/orders/{id}/ship`，成功后刷新列表。
- **详情抽屉**（`n-drawer`，宽 720+）：订单信息 `n-descriptions` + 商品明细列表 + 状态流转 `n-timeline`（`statusLogs`，operator 标注 用户/系统/管理员）+ 物流信息（公司/单号/轨迹，已发货时展示）。

### 6.4 API 层（沿用 http.ts 契约与 normalizePage）

```ts
export interface AdminOrderQuery {
  page: number; pageSize: number
  orderState?: number | null; orderSource?: number | null
  keyword?: string; start?: string; end?: string
}

export const listOrders = async (params: AdminOrderQuery) => {
  const page = await http.get<PageResult<AdminOrder>, PageResult<AdminOrder>>('/admin/orders', { params })
  return normalizePage(page)
}
export const getOrder = (id: EntityId) => http.get<AdminOrder, AdminOrder>(`/admin/orders/${id}`)
export const shipOrder = (id: EntityId, payload: { companyId: EntityId; logisticsNo: string }) =>
  http.put<AdminOrder, AdminOrder>(`/admin/orders/${id}/ship`, payload)
export const listLogisticsCompanies = () =>
  http.get<LogisticsCompany[], LogisticsCompany[]>('/admin/orders/logistics/companies')
```

## 七、验收路径

1. C 端下单并支付（`payOrder` mock 秒成功，1→2 到待发货）→ admin 待发货 Tab 可见该订单，列表字段完整；
2. 点发货 → 选公司/填单号 → 保存后状态变「待收货」，`order_logistics` + `order_logistics_track` + `order_status_log(ADMIN)` 各落 1 条；
3. 重复点发货 → 报「订单非待发货状态，无法发货」，不产生脏数据；
4. 秒杀订单（`order_source=2`）在列表正常展示、正常发货；
5. 筛选（状态/来源/关键词/时间范围）、分页、详情时间线、物流展示全部正常；
6. 前端发货弹窗空值校验、待发货徽标、秒杀 tag 正确。
