# 服务内鉴权缺失修复文档

## 问题是什么

当前网关会校验 token 并向下游注入 `X-User-Id`，但部分业务服务没有引入 `mall-common-security`，服务自身不校验 JWT。

典型服务：

- `mall-order-service`
- `mall-product-service`
- `mall-marketing-service`
- `mall-ai-service`
- `mall-admin-service`

这些服务中的 controller 直接信任 `X-User-Id`。如果请求绕过网关直连服务端口，就可以伪造用户 ID。

## 影响

- 用户可伪造 `X-User-Id` 操作他人订单、购物车、优惠券或秒杀。
- 服务端口误暴露后，网关鉴权形同虚设。
- 内网横向移动时可直接调用业务接口。
- 审计日志中的用户身份不可信。

## 怎么修复

### 1. 所有 Servlet 业务服务引入 `mall-common-security`

至少这些服务需要加入依赖：

```xml
<dependency>
    <groupId>com.hyf</groupId>
    <artifactId>mall-common-security</artifactId>
</dependency>
```

适用模块：

- `mall-order-service/pom.xml`
- `mall-product-service/pom.xml`
- `mall-marketing-service/pom.xml`
- `mall-admin-service/pom.xml`

`mall-ai-service` 当前同时有 WebFlux/Web MVC 特性，需单独评估。如果继续走 Servlet MVC，可以引入同一拦截器；如果纯 WebFlux，需要实现 reactive 版本鉴权过滤器。

### 2. 配置服务白名单

每个服务只放行真正公开接口。示例：

```yaml
mall:
  security:
    enabled: true
    exclude-paths:
      - /health/**
      - /products/**
      - /categories/**
```

订单服务不应放行 `/orders/**`、`/pay/**`，支付回调例外必须单独设计签名验证。

### 3. controller 不再信任外部传入的 `X-User-Id`

业务代码应从 `SecurityContextHolder` 获取登录用户：

```java
Long userId = SecurityContextHolder.getRequiredLoginUser().getUserId();
```

如果保留 `X-User-Id`，也必须只接受网关或内部可信调用注入的请求。

### 4. 内部调用增加可信来源标识

Feign 内部调用建议使用：

- 原始 `Authorization` 透传。
- 内部服务签名头，例如 `X-Internal-Signature`。
- 或 mTLS / service mesh 身份认证。

不要只依赖 `source-client` 这种客户端可伪造头。

### 5. 网络层禁止直连服务端口

部署层面必须保证：

- 对公网只暴露 gateway。
- 业务服务端口只允许网关、安全运维网段、服务间通信访问。
- Nacos、Sentinel、RabbitMQ、Redis、MySQL 不对公网开放。

## 验证方式

1. 不带 token 直连 `mall-order-service:8082/orders` 应返回 401。
2. 带伪造 `X-User-Id` 但不带合法 token，应返回 401。
3. 经网关带合法 token 请求，应正常返回。
4. token 用户 ID 与请求中伪造 `X-User-Id` 不一致时，应以 token 为准。
